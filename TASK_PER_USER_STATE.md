# Задача: персональные сессии и постоянное состояние обработки

Статус: **не реализовано**. Файл — техническое задание для следующего агента.

## Цель

Сделать так, чтобы состояние обработки и история файлов:

- хранились **на сервере в файлах**, а не только в памяти процесса и IndexedDB браузера;
- были **строго разделены по пользователям**: каждый видит только свои задания, файлы и историю;
- восстанавливались после перезагрузки страницы, повторного входа и перезапуска сервера;
- передавались между браузером и сервером через **серверную сессию**, без отправки логина и пароля в каждом запросе.

База данных не нужна — только файлы.

## Как устроено сейчас (отправная точка)

- `main.py`:
  - `JOBS: Dict[str, Dict[str, Any]] = {}` — все задания в памяти процесса, привязаны к `job["user"]`.
  - `_run_job()` обновляет задание через `_update_job()` и держит прогресс только в этом словаре.
  - `JOB_RETENTION_SECONDS = 24 * 60 * 60`; `_prune_jobs()` вызывается только при новой загрузке.
  - `POST /api/process` сохраняет исходник в `data/uploads/{login}_{uid}_{name}`.
  - Результат пишется в общую `data/outputs/masked_{uid}_{name}`.
  - `GET /api/jobs` фильтрует `JOBS` по логину, `GET /api/jobs/{id}` проверяет владельца.
  - `GET /api/download/{filename}` проверяет только авторизацию, но **не владельца** файла.
  - Аутентификация: заголовки `X-Login` / `X-Password` в каждом запросе, `data/users.json` (пароли в открытом виде).
- `index.html`:
  - `sessionStorage["creds"]` хранит логин и пароль.
  - IndexedDB `pii_masker_state` / `items` хранит снимок очереди: имя, статус, процент, превью, ссылку.
  - `restoreQueue()` при загрузке/логине восстанавливает таблицу, `pollUntilDone()` опрашивает `/api/jobs`.
  - Поэтому после F5 прогресс «не теряется»: настоящий прогресс лежит в RAM сервера, а таблица — в IndexedDB браузера.

## Целевая схема

### Файлы на диске

```
data/
  users.json                         # без изменений: список пользователей
  sessions/
    <session_id>.json                # серверная сессия, по файлу на сессию
  state/
    <user_dir>/
      jobs/
        <job_id>.json                # одно задание = один файл (история + текущий прогресс)
  uploads/
    <user_dir>/
      <uid>_<original_name>          # удаляется после обработки
  outputs/
    <user_dir>/
      <uid>_<original_name>          # готовый обезличенный файл
  activity.log
  server.log
```

`<user_dir>` — безопасное имя папки: логин, очищенный от недопустимых символов, плюс короткий хэш, чтобы не было коллизий и обхода путей. Пример:

```python
safe = re.sub(r"[^A-Za-z0-9_.@-]", "_", login)[:64]
user_dir = f"{safe}_{hashlib.sha1(login.encode('utf-8')).hexdigest()[:8]}"
```

Все пути строить только через `Path.resolve()` и проверять, что результат лежит внутри ожидаемой базовой папки.

### Файл сессии

`data/sessions/<session_id>.json`:

```json
{
  "version": 1,
  "login": "admin",
  "created": 1763500000.0,
  "last_seen": 1763500123.4,
  "expires": 1763543200.0
}
```

Правила:

- `session_id = secrets.token_urlsafe(32)`, в лог не писать.
- TTL по умолчанию 12 часов, настраиваемый `session_ttl_hours`; продление при активности (`session_sliding`, по умолчанию `true`).
- В файле **не должно быть пароля**.
- `POST /api/logout` удаляет файл сессии.
- Просроченные файлы удаляются при логине и/или фоновой чистке.
- Битый JSON: переименовать в `*.corrupt`, залогировать, считать сессию недействительной.

### Файл задания

`data/state/<user_dir>/jobs/<job_id>.json`:

```json
{
  "version": 1,
  "id": "8f3c...",
  "user": "admin",
  "filename": "договор.pdf",
  "size": 123456,
  "status": "processing",
  "progress": 42,
  "stage": "Поиск персональных данных",
  "elapsed": 12.3,
  "error": "",
  "created": 1763500000.0,
  "started": 1763500001.0,
  "finished": null,
  "out_name": "1234abcd_договор.pdf",
  "download_name": "masked_договор.pdf",
  "result": null
}
```

- `status`: `queued` | `processing` | `done` | `error`.
- `result` записывается только для `done`; превью и `extras` ограничить теми же лимитами, что сейчас (превью ~1800 символов, extras до 80).
- Запись **атомарная**: писать во временный файл в той же папке и делать `os.replace()`.
- Прогресс писать не чаще одного раза в 2 секунды на задание (`jobs_flush_seconds`), но смену статуса, этапа, ошибку и финал — всегда сразу.
- Список истории — это просто все `*.json` в папке `jobs`, отсортированные по `created`.
- Файлы заданий старше `history_retention_days` (по умолчанию 30) удалять вместе с их `outputs`, если задание завершено.

### Запуск сервера

При старте:

1. Создать `data/sessions`, `data/state`.
2. Пройти по всем `data/state/*/jobs/*.json`.
3. Задания со статусом `queued`/`processing` пометить как `error`:
   `"Сервер был перезапущен — обработка прервана"`, `finished = now`, `progress = 0`.
   Автоматическое продолжение обработки — **вне рамок задачи**.
4. Удалить оставшиеся исходники из `data/uploads/<user_dir>/` (они уже не нужны).
5. Удалить просроченные сессии и старые завершённые задания по retention.
6. Битые JSON не должны ронять сервер.

## Сессия и API

### Аутентификация

- `POST /api/login` — как сейчас принимает `{login, password}`, проверяет по `users.json`, создаёт файл сессии и возвращает:

```json
{ "ok": true, "login": "admin", "session_id": "...", "expires": 1763543200.0 }
```

- Все защищённые эндпоинты читают заголовок `X-Session: <session_id>`.
- `get_current_user()` ищет файл сессии, проверяет срок, продлевает `last_seen`/`expires`, возвращает `login`.
- Старые заголовки `X-Login`/`X-Password` можно оставить как временный fallback, но фронтенд должен перейти на `X-Session`.
- `GET /api/me` возвращает `{login, expires}` по сессии.
- `POST /api/logout` удаляет сессию.
- На любой 401 фронтенд очищает локальную сессию и показывает форму входа.

### Задания

- `POST /api/process`:
  - сохраняет исходник в `data/uploads/<user_dir>/`;
  - создаёт файл задания в `data/state/<user_dir>/jobs/`;
  - запускает поток;
  - возвращает те же поля, что сейчас (`job_id`, `filename`, `status`, `progress`).
- `GET /api/jobs` — читает только папку текущего пользователя. Чужие файлы не сканируются.
- `GET /api/jobs/{job_id}` — ищет файл только в папке текущего пользователя; иначе 404.
- `GET /api/download/{filename}` — либо оставить, но проверять, что файл лежит в `data/outputs/<user_dir>/` текущего пользователя, либо добавить `GET /api/jobs/{job_id}/download` и перевести фронтенд на него. Рекомендуется второй вариант: владение проверяется по файлу задания, а не по имени.
- `/api/health` не менять, кроме возможного `sessions_count`.

### Ограничения и конкурентность

- `PROCESS_LOCK` оставить: LM Studio обрабатывает один документ за раз.
- На каждое задание — свой файл, поэтому запись прогресса разных заданий не конфликтует.
- Для чтения-изменения-записи одного файла использовать `threading.RLock` (словарь локов по `job_id`) либо полагаться на то, что писатель у задания один.
- Создание/удаление файлов — под общим локом реестра.
- Никаких блокирующих запросов к LLM внутри lock.

## Изменения во фронтенде (`index.html`)

1. `sessionStorage` хранит **только** `session_id` (ключ, например, `session`). Пароль после логина нигде не сохранять.
2. `headers()` возвращает `{ "X-Session": sessionId }` вместо `X-Login`/`X-Password`.
3. `login()` сохраняет `session_id`, `logout()` вызывает `/api/logout` и очищает `session`.
4. `restoreQueue()`:
   - источник истины — `GET /api/jobs` для текущего пользователя;
   - IndexedDB можно оставить **только для ещё не отправленных файлов** (blob-ы, которые пользователь добавил, но не нажал «Обработать»);
   - сохранённые статусы/прогрессы/превью из IndexedDB больше не считать истиной.
5. После логина показывать историю именно этого пользователя; при смене пользователя в том же браузере список полностью перезагружается с сервера.
6. Скачивание — по ссылке из задания (с проверкой владельца на сервере).

## Что считать готовым (критерии приёмки)

1. Загрузили файл, перезагрузили страницу — прогресс и этап продолжают идти, значения совпадают с серверным файлом задания.
2. Закрыли браузер, открыли снова, вошли тем же пользователем — видна его история, включая завершённые задания и ссылки на скачивание.
3. Вошли другим пользователем в том же браузере — видны только его задания; чужие не отображаются.
4. Перезапустили сервер во время обработки — после старта задание имеет статус `error` с понятным текстом, сервер работает, остальные задания и история целы.
5. Прямой запрос `/api/jobs/{чужой_id}` и скачивание чужого файла возвращают 404/403.
6. В `sessionStorage` и в запросах после логина нет пароля; в файлах сессий нет пароля.
7. Два пользователя обрабатывают файлы по очереди — состояния не смешиваются.
8. Испорченный JSON задания/сессии не роняет сервер.
9. Старые завершённые задания и их файлы удаляются по retention.
10. `python -m py_compile main.py` проходит; сценарии 1–5 проверены вручную.

- Несколько экземпляров сервера на одной папке `data`.

## Риски и замечания

- Файлы заданий и сессий содержат имена файлов и результаты превью — это те же данные, что уже лежат в `data/outputs`; права доступа к папке `data` должны быть ограничены.
- Частая запись прогресса на диск может замедлить обработку — обязателен троттлинг.
- Старые результаты в текущей плоской `data/outputs` не привязаны к пользователям. Новый код не должен отдавать их как чужие: либо оставить доступ только через новую схему, либо одноразово перенести в `outputs/admin/`.
- При смене пользователя в одном браузере IndexedDB с неотправленными файлами может содержать файлы предыдущего пользователя. При logout очищать локальную очередь неотправленных файлов (или явно предупреждать).
